# Holler protocol v1

Holler is a **talk circuit**. This page is the v1 application protocol: JSON messages on a WebSocket between **holler-server** and **holler-client**.

It is not SSH, not ACP, and not a chat with a model. ACP (and OpenCode HTTP) live **behind** the client, as a body adapter.

**This file is canonical.** ADRs decide why; stories implement this page. There is no v0.

## 1. Transport

WebSocket **text** frames. One JSON object per frame.

Confidentiality is **TLS 1.3 on `wss`** ([ADR 0010](../adr/ADR-0010.md)): AES-256-GCM or ChaCha20-Poly1305. Plain `ws` is **loopback only**. Join secrets are HMAC-SHA-256 at rest; they are never logged.

Listen address is user-settable (`--listen` / `HOLLER_LISTEN`). Default **`127.0.0.1:41807`** ([ADR 0004](../adr/ADR-0004.md)). Omitted port on a join URL is 41807.

Any underlay (LAN, SSH tunnel, Tailscale, public IP) may create the TCP path. It is not Holler auth, not Holler addressing, and **not Holler encryption**.

## 2. Version

Two different numbers:

| Field | Meaning |
| --- | --- |
| Envelope `"v"` | Version of **this connection**. A v1 session always sends `1`. |
| `protocol_min` / `protocol_max` | Lowest / **highest** version **this binary** implements. |

`hello` advertises min/max (a hint). **`query protocol` is the check.** The client answers with the highest version it can handle, even if this socket is speaking v1.

A v1 server requires envelope `v == 1`. If the peer cannot speak 1 (`protocol_min > 1`, or envelope `v` missing / not `1`), reply `error` with `code: unsupported_version` and close. **No silent downgrade of the session.** Advertising `protocol_max: 2` on a v1 socket is a capability answer, not a downgrade.

Today every process has `min = 1`, `max = 1`.

## 3. Envelope

```json
{
  "v": 1,
  "type": "hello",
  "id": "01JEXAMPLE0000000000000000",
  "ts": "2026-09-05T19:30:00Z",
  "from": "tok_7f3a",
  "body": {}
}
```

| Field | Rule |
| --- | --- |
| `v` | Always `1` in this document |
| `type` | One of the types below |
| `id` | Correlation id (ULID or UUID). Replies reuse the request `id` |
| `ts` | UTC, RFC 3339 |
| `from` | Client: public `token_id`. Server peer: `"server"` |
| `body` | Object; shape depends on `type` |

Unknown `type` → `error` / `unknown_type`. Do not ignore it as success.

## 4. Connection

```
connect  →  auth  →  hello (both ways)  →  talk / query / ping
```

1. Client opens the WebSocket.
2. Client sends `auth` with the **client credential** (not the join secret). First-frame auth is allowed; do not put the credential in a logged URL query string.
3. Each side sends `hello` (capabilities + hostname).
4. After both hellos, `prompt` / `query` / `ping` are legal.

Reconnect uses the credential again. A new join token is only for a new pairing.

## 5. Message types

| `type` | Who | Job |
| --- | --- | --- |
| `auth` | client → server | Present credential |
| `hello` | both | Protocol version, hostname, features, harnesses, sessions |
| `query` | both | Command + args (`status`, `caps`, `support`, `protocol`) — **not** a prompt |
| `query_ok` | both | Structured answer to `query` |
| `prompt` | server → client | Prompt a named session |
| `reply` | client → server | Session output / turn result |
| `interrupt` | server → client | Cancel the **turn**; session lives |
| `presence` | client → server | Session advertise + heartbeat |
| `ping` / `pong` | both | Bound-socket aliveness (`holler token ping`) |
| `ack` | both | Optional receipt |
| `error` | both | Typed failure |

`interrupt` is control, not a `prompt` (ADR 0005). `query` is control, not a `prompt`. Never route `query`, `support`, or `protocol` into a model.

## 6. `hello` — advertise, don’t guess

Client:

```json
{
  "v": 1,
  "type": "hello",
  "id": "01JHELLOCLIENT000000000000",
  "from": "tok_7f3a",
  "body": {
    "protocol": 1,
    "protocol_min": 1,
    "protocol_max": 1,
    "role": "client",
    "hostname": "kiwi",
    "token_id": "tok_7f3a",
    "client_id": "cli_19",
    "features": ["interrupt", "presence", "ping", "query"],
    "harnesses": ["opencode"],
    "sessions": [
      {"name": "alpha", "harness": "opencode"},
      {"name": "beta", "harness": "opencode"}
    ]
  }
}
```

Server (the hub is a **peer** for status — same document shape, `role: server`):

```json
{
  "v": 1,
  "type": "hello",
  "id": "01JHELLOSERVER00000000000",
  "from": "server",
  "body": {
    "protocol": 1,
    "protocol_min": 1,
    "protocol_max": 1,
    "role": "server",
    "hostname": "uranus",
    "features": ["interrupt", "presence", "ping", "query", "roster", "token"],
    "harnesses_known": ["opencode"],
    "harnesses_confirmed": ["opencode"]
  }
}
```

**Advertise only what is real.** A client lists a harness only if it can spawn that adapter on this box (binary or ACP on PATH, adapter compiled in). Do not list `claude` because it appears on the server’s roadmap.

`hello` is a hint. **`query` / `support` is the check.**

## 7. `query` — commands and arguments, not an LLM

`body.cmd` is a command. `body.args` is a string array. Unknown `cmd` → `error` / `unknown_cmd`. Do not invent an answer.

| `cmd` | `args` | Meaning |
| --- | --- | --- |
| `status` | none | Who are you, are you up, what do you have |
| `caps` | none | Full capability document (status + support map) |
| `support` | `[feature]` | Boolean: do you support this feature or harness **right now** |
| `protocol` | none or `[version]` | Highest version this binary can handle; optional “can you speak N?” |

### `support`

Request (server asking a client “do you support OpenCode?”):

```json
{
  "v": 1,
  "type": "query",
  "id": "01JQUERYSUPPORT0000000000",
  "from": "server",
  "body": { "cmd": "support", "args": ["opencode"] }
}
```

Answer:

```json
{
  "v": 1,
  "type": "query_ok",
  "id": "01JQUERYSUPPORT0000000000",
  "from": "tok_7f3a",
  "body": {
    "cmd": "support",
    "args": ["opencode"],
    "ok": true,
    "feature": "opencode",
    "kind": "harness",
    "how": "opencode acp"
  }
}
```

`ok: false` example:

```json
{
  "cmd": "support",
  "args": ["claude"],
  "ok": false,
  "feature": "claude",
  "kind": "harness",
  "reason": "no adapter"
}
```

How a **client** decides `ok` for a harness: local probe (adapter + runnable binary/ACP). Not “ask the model.” Not “the server checklist includes it.”

How the **server** decides `ok` for a harness:

| Field | Meaning |
| --- | --- |
| `known` | This id is in the v1 vocabulary (issue #1 list) |
| `confirmed` | At least one **live** client answered `support` with `ok: true` (hello advertisement is not enough by itself) |
| `ok` | For harnesses: `confirmed`. For protocol features (`interrupt`, `query`, …): this process implements them |

The client may `query` the server the same way. The server answers as a peer (`from: "server"`).

### `protocol`

The server asks the client (or the client asks the server) what versions that **binary** can speak. This is not “what is `v` on this socket.”

No args — report range; `max` is the highest it can handle:

```json
{
  "v": 1,
  "type": "query",
  "id": "01JQUERYPROTOCOL000000000",
  "from": "server",
  "body": { "cmd": "protocol", "args": [] }
}
```

```json
{
  "v": 1,
  "type": "query_ok",
  "id": "01JQUERYPROTOCOL000000000",
  "from": "tok_7f3a",
  "body": {
    "cmd": "protocol",
    "session": 1,
    "min": 1,
    "max": 1
  }
}
```

With an argument — “can you handle this version?” (`ok` is `asked >= min && asked <= max`):

```json
{ "cmd": "protocol", "args": ["2"] }
```

```json
{
  "cmd": "protocol",
  "args": ["2"],
  "ok": false,
  "asked": 2,
  "session": 1,
  "min": 1,
  "max": 1
}
```

`args[0]` must be a positive integer; otherwise `error` / `unknown_feature`. Do not ask a model. A later binary with `max: 2` still uses envelope `v: 1` on a v1 server.

### `status` document

Same schema whether the local process is the server or a client. That is what “the server as a client for its status” means: **one document**, two `role` values.

Client:

```json
{
  "cmd": "status",
  "role": "client",
  "protocol": 1,
  "protocol_min": 1,
  "protocol_max": 1,
  "hostname": "kiwi",
  "connected": true,
  "token_id": "tok_7f3a",
  "features": ["interrupt", "presence", "ping", "query"],
  "harnesses": ["opencode"],
  "sessions": [
    {"name": "alpha", "harness": "opencode", "busy": false}
  ]
}
```

Server:

```json
{
  "cmd": "status",
  "role": "server",
  "protocol": 1,
  "protocol_min": 1,
  "protocol_max": 1,
  "hostname": "uranus",
  "listening": "wss://example.example:41807",
  "features": ["interrupt", "presence", "ping", "query", "roster", "token"],
  "harnesses_known": ["opencode"],
  "harnesses_confirmed": [
    {"id": "opencode", "clients": ["kiwi"]}
  ],
  "clients": 1,
  "sessions": 2
}
```

`caps` is `status` plus an explicit map of every known feature/harness → `{ok, kind, reason?}`.

## 8. CLI mapping

Local (no target) talks to **this process**. With a target, the server sends `query` over the wire.

| CLI | Wire |
| --- | --- |
| `holler status` | local `query status` |
| `holler status <id>` | `query status` to that client (token id, client id, hostname, or session → hosting client) |
| `holler support <feature>` | local `query support [feature]` |
| `holler support <id> <feature>` | `query support [feature]` to that client |
| `holler caps` / `holler caps <id>` | `query caps` |
| `holler query <cmd> [args…]` | general form |
| `holler query <id> <cmd> [args…]` | general form, remote |
| `holler query protocol` / `holler query <id> protocol` | `query protocol` — highest version this binary (or that client) can handle |
| `holler query protocol <n>` / `holler query <id> protocol <n>` | can you speak version `n`? |
| `holler token ping <id>` | `ping` / `pong` (not `query`) |

`--json` prints the `query_ok` body.

One-argument `holler support X`: if `X` is a known feature or harness id, it is local; otherwise it is a target and the command errors with “missing feature”. Feature ids are reserved words.

## 9. Feature and harness ids

**Protocol features** (v1): `interrupt`, `presence`, `ping`, `query`, `roster`, `token`, `wait`.

**Harness ids** (vocabulary; only `opencode` is a v1 adapter):

`opencode`, `claude`, `codex`, `grok`, `hermes`, `pi`, `cursor`, `copilot`, `droid`, `kimi`, `qwen`, `kilo`, `goose`.

A new harness is a new **config row** (and, if needed, an out-of-tree ACP adapter), plus a new id. It is not a new protocol version and not a Holler release ([ADR 0011](../adr/ADR-0011.md)). Unknown ids are legal.

## 10. Talk frames (sketch)

Enough to implement routing. Details that belong to adapters stay in ADR 0005 / 0008.

**`prompt`** — `body.session` (name), `body.text`, optional `body.meta`.

**`reply`** — `body.session`, `body.text` and/or `body.chunks`, `body.done` (bool), optional `body.exit`.

**`interrupt`** — `body.session`. Client maps to ACP `session/cancel` (HTTP interrupt fallback). Session remains promptable. Picture: [talk.md](talk.md).

**`presence`** — advertised sessions + heartbeat. Server drops stale rows from `holler roster` (ADR 0006).

**`ping` / `pong`** — empty or `{hostname}`. Used by `holler token ping`, not by roster.

## 11. Errors

```json
{
  "v": 1,
  "type": "error",
  "id": "01JQUERYSUPPORT0000000000",
  "from": "tok_7f3a",
  "body": {
    "code": "unknown_cmd",
    "cmd": "summarize",
    "message": "unknown query cmd"
  }
}
```

| `code` | When |
| --- | --- |
| `unsupported_version` | `v` ≠ 1 |
| `unauthenticated` | `auth` missing or revoked |
| `unknown_type` | unknown envelope type |
| `unknown_cmd` | unknown `query` cmd |
| `unknown_feature` | `support` id is not in the vocabulary |
| `unknown_session` | prompt/interrupt to a name this client does not host |
| `not_connected` | server `query`/`ping` to a bound token with no live socket |

## 12. Four different questions

| Ask | Answers |
| --- | --- |
| `holler status` / `query status` | Who is this process; is the circuit up; which harnesses are **confirmed** |
| `holler query protocol` | Highest protocol version this binary can handle |
| `holler support …` / `query support` | Do **you** support X, right now |
| `holler roster` | Which **sessions** can be hollered at (presence TTL) |
| `holler token ping` | Is this **bound WebSocket** alive |

## 13. Not in v1

- A second protocol dialect (“v0”)
- Using a model to answer `support` or to invent cmds
- SSH or Tailscale as the app protocol; secrets in logged URLs or at `quiet`/`noisy` debug
- Multiplexing PTYs; merging Herdr sockets
- Binary frames, multi-hop routing, Nostr
