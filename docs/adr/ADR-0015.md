# ADR 0015 — Join redeem is a dedicated wire frame, not overloaded `auth`

**Status:** accepted
**Issue:** #16
**Date:** 2026-09-06

## The gap this closes

`docs/protocol/v1.md` §4 says the client sends `auth` with "**the client credential** (not the join secret)." The 12 v1 message types (`auth`, `hello`, `query`, `query_ok`, `prompt`, `reply`, `interrupt`, `presence`, `ping`, `pong`, `ack`, `error`) have no frame for turning a one-time join secret into a credential over the network. This was discovered mid-implementation: holler-client #23 built `holler join --server <url> --token <t>` as a one-command CLI expecting to redeem over the wire; holler-server #30 built a fully-real `TokenStore::redeem()`; holler-server #31 wired `auth` to only call `verify_credential`, matching the spec exactly. Neither story was wrong — the wire protocol simply never defined how the two sides meet. holler-client #24's PR flagged this prominently and left `JoinTransport` stubbed rather than invent an answer unilaterally.

## Options considered

1. **A dedicated `join` / `join_ok` frame pair.** Client sends `join` (secret + hostname) as the first frame on a fresh, unauthenticated connection; server redeems and replies `join_ok` (client_id + credential) or `error`.
2. **Overload `auth`** to accept either a credential or a join secret, branching on which one was presented. Fewer message types, but reverses the spec's current explicit statement and mixes two different trust levels through one field.
3. **No network redeem at all** — treat join as purely operator-mediated (server operator runs `redeem` locally, hands the resulting credential to the client operator by hand). Matches the stopgap that exists today, but contradicts both #23's and #30's own issue text, which frame `holler join --token` as a single command the *client* runs.

## Prior art for the shape

Two real CLI precedents, checked directly rather than assumed:

- **`gh`/`glab`** (GitHub/GitLab CLIs) use OAuth's **Device Authorization Flow** (RFC 8628): the CLI shows a challenge code, a human approves it in a **browser** elsewhere, the CLI polls until authorized. Built for headless machines, but it requires a browser+human-approval step in the loop — wrong shape here, since Holler's `join` is deliberately CLI-only and the "approval" already happened when the operator ran `holler token mint` on the server.
- **Terminus** (Pantheon's CLI) is structurally the closest match: a **machine token**, generated once in a dashboard and shown only once at creation, then `terminus auth:login --machine-token=<token>` makes one network call to exchange it for a working session. This is exactly `holler token mint` (secret shown once) → `holler join --token <t>` (one network call to redeem it) — it validates the "out-of-band secret, one CLI-driven exchange" shape. One deliberate difference: Terminus's machine token doesn't expire and is reused directly as the ongoing credential; Holler's one-time secret is *consumed* and replaced by a separate long-lived credential (closer to an OAuth refresh-token exchange), so a leaked mint transcript is useless after the one redeem.

## Decision

**Option 1.** A dedicated `join`/`join_ok` frame pair, specified in `docs/protocol/v1.md` §4.1. v1 has not shipped past its acceptance gate yet, so adding this now is finishing v1, not a breaking change (ADR 0014's versioning rules: this is additive, not BC-breaking).

Key design points:
- `join` is legal **only** as the first frame on a connection that has not yet sent/received `auth` — a connection sends `join` or `auth`, never both.
- The envelope `from` field carries the join **token_id** (already known publicly at mint time, per #29 — this is not the secret, and needs no new envelope convention).
- On success, the server replies `join_ok` and **closes the connection**. It does not continue into `hello`/talk on the same socket. `join` is a one-shot bootstrap; the client persists its new credential and reconnects via the ordinary `auth` → `hello` flow to actually start a session. This requires zero changes to the already-built `auth`/`hello`/reconnect logic (holler-client #24) — only `holler join`'s redeem step gains a real network implementation.
- Failure is the existing `error` envelope with one new code, `join_failed` (covers: secret not found, already bound, invalidated, revoked, expired — the specific reason goes in `error.message`, not a proliferation of wire codes, matching this protocol's existing fail-closed-but-not-overly-granular style).

## Consequences

- `docs/protocol/v1.md` gains `join`/`join_ok` in §5's type table and a new §4.1, plus `join_failed` in §11's error table. No existing section is renumbered (existing `§N` code-comment citations elsewhere in both repos stay valid).
- holler-server: `src/proto/mod.rs` gains `Body::Join`/`Body::JoinOk` variants; `src/wire/connection.rs`'s first-frame handling branches on `Auth` vs `Join` instead of assuming `Auth`; the already-real `TokenStore::redeem()` (#30) is finally reachable from a live connection.
- holler-client: `src/join.rs`'s `JoinTransport` gets a real implementation (a short-lived connection: connect → `join` → `join_ok`/`error` → close), replacing `StubJoinTransport` for production use. The stub may stay as a test double.
- Tracked as follow-up implementation issues once this ADR lands (one per repo, cross-linked).
