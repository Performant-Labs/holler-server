# ADR 0011 — New harnesses are config, not Holler releases

**Status:** accepted  
**Issue:** #12  
**Date:** 2026-09-05

## Decision

**Do not ship an in-process plugin API. Do not cut a Holler release for each new harness.**

holler-server already treats harness ids as strings (`opencode`, `claude`, …). A new harness is **not** a protocol version and **not** a server change.

holler-client ships **one** in-tree driver: spawn a subprocess that speaks **ACP** (JSON-RPC stdio), map `prompt` / `reply` / `interrupt` / presence. Bodies are **config**:

```toml
[[session]]
name = "alpha"
harness = "opencode"
command = ["opencode", "acp"]
# interrupt defaults to ACP session/cancel
```

```toml
[[session]]
name = "reviewer"
harness = "claude"
command = ["claude-agent-acp"]
```

If the harness (or a thin wrapper) already speaks ACP, **Holler’s code does not change.** `holler support claude` is “can this box exec the configured command,” not “did we compile Claude in.”

If a harness does **not** speak ACP: an **out-of-tree adapter binary** that does (separate repo, separate release). Holler still only `exec`s `command`. The adapter is not loaded into Holler’s process.

v1 ships OpenCode as the **default config** (ADR 0008), including the HTTP interrupt fallback as an optional config field — not as a second plugin system.

## Why not plugins, why not a release train

| Approach | Why it is miserable for a solo maintainer |
| --- | --- |
| Release holler-client every time Claude/Codex/Grok drifts | You own every vendor’s CLI. Forever. |
| In-process plugins (Go plugins, npm `require`, dylibs) | You own a public Plugin API, ABI breaks, and other people’s crashes in your process. |
| Server-side adapters | The hub would know about bodies. ADR 0001 / 0002 forbade that. |

ACP *is* the extension point. Buzz already treats the harness command as configurable behind ACP; we take that *shape*, not their code.

## Consequences

- Issue #1’s harness checklist is a **docs/gate** list, not a compile-time enum. Unknown `harness` ids are legal on the wire.
- Checking a box on #1 means: a config snippet exists, `holler support <id> <harness>` is true, and the two-session gate (or equivalent) was run. It does **not** mean a Holler version bump.
- holler-server never gains a `switch harness` of vendor SDKs.
- Convenience later (`holler body add opencode`) may **write config** if the binary is on PATH. That is sugar.
- OpenCode HTTP interrupt stays a **configured** fallback for v1, not a hardcoded special case that every future harness copies in-tree.

## Not in v1

- A plugin marketplace, Go plugins, or npm adapter host
- Compiling Claude/Codex/Grok into holler-client
- A Holler protocol bump to add a harness id
