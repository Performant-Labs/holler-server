# ADR 0014 — Versioning: SemVer per crate, starting at 0.1.0, independent per repo

**Status:** accepted
**Issue:** #15
**Date:** 2026-09-06

## Decision

Each of holler-server and holler-client is versioned independently, in its own `Cargo.toml`, starting at **0.1.0** (already the scaffold default in both — this ADR ratifies it as policy, not an accident of `cargo init`).

Semantic Versioning (`MAJOR.MINOR.PATCH`), applied consistently from 0.1.0 onward:

- **PATCH** — security fixes and other minor changes: bug fixes, behavioral corrections that are not new capabilities, dependency bumps, internal refactors with no visible surface change.
- **MINOR** — new features: a new CLI subcommand or flag, a new capability, anything additive that does not change or remove existing behavior.
- **MAJOR** — anything that breaks backward compatibility (see "What counts as breaking," below).
- **Client and server move independently.** A holler-client release does not imply anything about holler-server's version, and vice versa. There is no shared/synchronized version number across the two repos.

**Deviation from default SemVer, stated explicitly:** standard SemVer allows a `0.x` major version to treat *any* change as non-breaking until 1.0.0 (major stays `0`, breaking changes bump `MINOR` instead). This project does **not** use that carve-out. From `0.1.0` on, a breaking change always bumps `MAJOR` — `0.1.0` → `1.0.0` the first time something actually breaks, not a slow drift through `0.x` while accumulating breakage. This matters because most SemVer tooling defaults to the standard behavior; anyone scripting against these version numbers should know this project opted out of it.

## Crate version is not the wire protocol version

Holler already has a separate version number: the wire protocol's `v` field and `protocol_min`/`protocol_max` negotiation (ADR 0009), currently pinned at `1`. **These are different axes and must not be conflated:**

- A crate's `MAJOR` bump (e.g. renaming a CLI flag, changing `--json` output shape) does not by itself mean the wire protocol changed. Both sides can keep speaking Holler protocol v1 across many crate major versions.
- A wire protocol version bump (v1 → v2) is a much bigger, jointly-coordinated event that affects both repos' ability to talk to each other at all — it is not decided unilaterally by either crate's own release cadence, and does not automatically follow this ADR's per-crate rules. If/when that happens, it gets its own ADR (claim the next reserved slot at that time).

## What counts as "breaking" here

Neither crate is published as a library dependency (no crates.io publication — see the naming-collision note in `docs/research-competitive-landscape.md`, where the name `holler` is already taken there). So "breaking" is scoped to this project's real compatibility surfaces:

- **CLI surface**: removing or renaming a subcommand or flag, changing required argument order, changing exit-code semantics that scripts might depend on.
- **`--json` output shape**: any field rename, removal, or type change in JSON output meant for scripting/meta-O consumption (per `docs/protocol/v1.md` §8's own framing of `--json` as a machine-readable contract). Additive fields are not breaking; removing or repurposing an existing field is.
- **On-disk file formats**: the token store (`holler-server`), the credential file and roster/session config (`holler-client`). A format change that an older binary can no longer read (without an explicit migration path) is breaking, even if the wire protocol and CLI are untouched.

Adding a new optional field, a new subcommand, or a new config key is additive — `MINOR`, not `MAJOR`.

## When a bump actually happens

Not on every merged PR. This project merges frequently and in small increments; bumping `Cargo.toml`'s `version` on every commit would produce version churn with no real meaning. A version bump happens at a deliberate **release point**: whoever cuts a release edits `version` once (reflecting everything accumulated since the last bump, per the highest-severity change in that batch — one `MAJOR` change anywhere in the batch means the whole bump is `MAJOR`), tags it (`vX.Y.Z`, since each repo has its own independent tag sequence), and records it in that repo's `CHANGELOG.md`.

## Consequences

- `Cargo.toml`'s `version` field is the single source of truth per repo; no workspace-wide version to keep in sync (each repo builds one crate).
- Each repo gets a `CHANGELOG.md` (Keep a Changelog style is fine) if one doesn't exist yet — not built retroactively for pre-ADR history, starting from this decision forward.
- `holler status`'s response document is a reasonable place to eventually surface the running binary's own crate version (operators and meta-O can already see protocol/hostname/features there) — not required by this ADR, just a natural fit for a later story if wanted.
- A future wire-protocol version bump (v1 → v2) is explicitly **not** governed by this ADR — it needs its own decision when it actually comes up.

## Not decided here

- The exact release mechanics (who/what cuts a release, whether it's manual `cargo set-version` or an automated tool like `cargo-release` or `release-plz`) — left to whoever sets up the first real release.
- Pre-release tags (`-alpha`, `-rc`) — not needed yet at this stage of the project.
