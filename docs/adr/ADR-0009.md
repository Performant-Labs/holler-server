# ADR 0009 — Protocol is Holler v1

**Status:** accepted  
**Issue:** #10  
**Date:** 2026-09-05

## Decision

The application protocol is **Holler v1**. The canonical spec is [`docs/protocol/v1.md`](../protocol/v1.md). There is no v0.

Every envelope carries `"v": 1`. `hello` advertises hostname, features, and harnesses the peer can actually drive. `query` asks a peer a **command with arguments** (`status`, `caps`, `support <feature>`). Answers are structured JSON. **Do not send a prompt to an LLM to decide whether a peer supports a feature.**

The **server is a peer** for status and capability. It answers the same `status` / `caps` / `support` document a client returns (`role: server`). `holler status` with no target is the local process describing itself. `holler status <id>` and `holler support <id> <feature>` send a `query` over the wire.

A harness is **confirmed** on the server only when a live client answers `support` with `ok: true`. A hello advertisement is a hint, not the check.

Issue [#28](https://github.com/Performant-Labs/holler-server/issues/28) implements this spec (it was drafted as “v0”; that name is retired).

## Why a versioned spec page

ADRs decide why (WebSocket not SSH, interrupt is control, tokens). Implementers need one page for the envelope, types, and query commands. A version number lets a later v2 hello fail closed (`unsupported_version`) instead of silently mixing frames.

## Consequences

- Implement #28 as protocol v1; do not ship a v0 dialect.
- Client speaks this document (holler-client ADR 0001) and answers `query` from local probes.
- `holler status` / `support` / `caps` / `query` are in the v1 CLI.
