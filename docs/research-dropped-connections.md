# Research memo — dropped connections (heartbeat, TTL, reconnect, in-flight replies)

**Status:** research / discussion memo — **not an ADR, not a decision**. Written to inform a future numbered ADR once the team has actually discussed and decided.
**Date:** 2026-09-05
**Related:** [ADR-0004](adr/ADR-0004.md) (transport), [ADR-0005](adr/ADR-0005.md) (interrupt is control, session survives), [ADR-0006](adr/ADR-0006.md) (presence is status), [ADR-0007](adr/ADR-0007.md) (session addressing), [protocol v1](protocol/v1.md), [talk.md](protocol/talk.md), holler-client issue [#24](https://github.com/Performant-Labs/holler-client/issues/24), holler-server issue [#32](https://github.com/Performant-Labs/holler-server/issues/32).

## 1. Scope

This memo does **not** re-litigate what's already decided:

- The underlying coding-agent session survives a dropped WebSocket (ADR-0005) — a drop cuts off *visibility*, not the process.
- Reconnect uses the **client credential**, never a fresh join token, unless detached/revoked (ADR-0004, issue #24).
- Presence/roster is heartbeat + TTL, stale rows drop out of `holler roster` after a **bounded** wait, never indefinitely (ADR-0006).
- Issue #24 already specifies "exponential backoff reconnect" for the client; issue #32 is where server-side TTL tuning lands.

What's still open, and what this memo researches: the **exact numbers** (heartbeat interval, missed-heartbeat threshold, backoff base/cap/jitter), what a **roster row** looks like while disconnected-but-maybe-coming-back, and what happens to a **turn's `reply`** if it finishes while the client is offline.

## 3. General best practice — primary sources

| # | Topic | Finding | Source |
| - | - | - | - |
| 1 | WebSocket ping/pong (RFC 6455) | Ping/Pong are control frames (opcodes `0x9`/`0xA`, ≤125-byte payload); a Pong **must** echo the Ping payload "as soon as practicable." The RFC sets **no mandated interval or timeout** — purely an application decision. | [RFC 6455 §5.5.2–5.5.3](https://www.rfc-editor.org/info/rfc6455/) |
| 1b | Practical heartbeat sizing | Recommended range **30–45s**, with a "75% of your shortest proxy idle timeout" rule (nginx/ALB default 60s idle → 45s heartbeat); **10s** pong-timeout before declaring a connection dead. | [websocket.org/guides/heartbeat](https://websocket.org/guides/heartbeat/) |
| 2 | Exponential backoff + jitter | Canonical source. **Full Jitter:** `sleep = random(0, min(cap, base * 2^attempt))`. **Equal Jitter:** `sleep = cap/2 + random(0, cap/2)`. **Decorrelated Jitter:** `sleep = min(cap, random(base, sleep*3))`. Conclusion: **Full Jitter wins** — least total client/server work, comparable-or-better completion time vs. Decorrelated; Equal Jitter is worst of the three. Both jittered strategies beat plain exponential backoff by a wide margin. | Marc Brooker, [AWS Architecture Blog](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/) |
| 3 | Phoenix Channels | JS client heartbeat defaults to **every 30s**; on drop, **channel rejoin is automatic with exponential backoff.** | [hexdocs.pm/phoenix/js](https://hexdocs.pm/phoenix/js/) |
| 4 | Socket.IO reconnection | Client defaults: `reconnection: true`, `reconnectionAttempts: Infinity`, `reconnectionDelay: 1000ms`, `reconnectionDelayMax: 5000ms`, `randomizationFactor: 0.5`, connect `timeout: 20000ms`. "Volatile" emits are dropped if not currently connected; normal emits buffer client-side and flush on reconnect (send-direction only, not durable event replay). | [socket.io/docs/v4/client-options](https://socket.io/docs/v4/client-options/) |
| 4b | Socket.IO Connection State Recovery | Added v4.6 (Feb 2023). Server retains a disconnected client's state for a configurable `maxDisconnectionDuration`; client reconnects with its last-processed offset; server attempts best-effort replay. Docs explicitly warn: **"recovery will not always be successful… must send at least one event to initialize the offset."** Opt-in, bounded, not guaranteed. | [socket.io/docs/v4/connection-state-recovery](https://socket.io/docs/v4/connection-state-recovery) |
| 5 | SignalR | Default automatic-reconnect backoff is a **fixed sequence: 0s, 2s, 10s, 30s**, then stops (4 attempts, then gives up unless the app supplies its own `IRetryPolicy`). A reconnect with negotiation skipped gets a **new** connection id (`null` on the `Reconnected` event) — no implicit session resume unless the app tracks its own identity. | [Microsoft Learn — SignalR .NET client](https://learn.microsoft.com/en-us/aspnet/core/signalr/dotnet-client) |
| 6 | gRPC keepalive | Client default `KEEPALIVE_TIME` **disabled** (`INT_MAX`), `KEEPALIVE_TIMEOUT` **20s**; server default `KEEPALIVE_TIME` **2h**, `KEEPALIVE_TIMEOUT` **20s**. Confirmed: **streaming RPCs do not auto-reconnect** — "if the connection is closed, any in-progress RPCs will fail… any data that has not yet been sent will be lost." Client must detect failure and open a fresh stream itself. | [grpc.io/docs/guides/keepalive](https://grpc.io/docs/guides/keepalive/) |
| 7 | mosh | Own UDP-based **State Synchronization Protocol (SSP)**, not TCP+reconnect. Syncs terminal *screen state*, not a byte stream — an offline client doesn't replay buffered output, it **snaps to current state** ("skips ahead to what the screen looks like now"). Session identity is bound to a crypto key, not an IP, so roaming across networks is transparent. Client heartbeats **at least every 3 seconds**; server retargets outgoing packets to whatever source address last sent an authenticated, higher-sequence-numbered packet. | [mosh.org](https://mosh.org/), [mosh-paper.pdf](https://mosh.org/mosh-paper.pdf) |
| 8 | SSH keepalive | `ClientAliveInterval` / `ServerAliveInterval` both **default to 0 (disabled)**. When enabled, `ClientAliveCountMax` / `ServerAliveCountMax` default to **3**; connection drops after `Interval × CountMax` seconds of silence. Pure liveness probe — SSH has no session-survives-the-drop model of its own (that's mosh's whole value proposition by contrast). | OpenSSH `sshd_config(5)` / `ssh_config(5)` |
| 9 | Missed-events-while-offline, general pattern | None of Phoenix Channels, plain Socket.IO, or gRPC provide durable replay **by default**. The dominant industry pattern is **"ask again on reconnect,"** not "replay what you missed." Durable replay is reserved for systems explicitly built as durable pub/sub (Kafka, SQS, Postgres-backed queues) — not general-purpose realtime channel libraries. Socket.IO's opt-in Connection State Recovery is the one partial exception, and even it is explicitly best-effort/bounded. | Same sources as #3, #4b, #6 |

## 4. The in-flight-turn question, specific to Holler

ADR-0005 already establishes that the **session** survives a drop — the ACP subprocess and its turn state live on the client box, independent of the Holler socket. The open question is narrower: if a turn's `reply` (protocol v1 §10: `body.session`, `body.text`/`body.chunks`, `body.done`) **completes while the hub's WebSocket to that client is down**, what happens to it?

Two shapes, matching the general pattern found in §3.9:

- **Durable delivery** — server (or client) buffers the reply and pushes it on reconnect, preserving ordering and exactly-once-ish delivery. This is the Socket.IO-Connection-State-Recovery shape: real, but explicitly bounded/best-effort even in a purpose-built implementation, and Socket.IO's is a whole subsystem (offset tracking, session id separate from socket id, adapter-level state storage) for a problem more general than Holler's.
- **Ask-again** — the reply is not resurrected; the roster/status document simply reflects "this session finished a turn" (or "this session is busy" → "not busy"), and meta-O (or the hub) re-queries current state on reconnect. This is the Phoenix/plain-Socket.IO/gRPC default shape, and Buzz's actual choice (fire-and-forget, no buffer, messages to a disconnected peer are lost).

**Recommendation: ask-again, not durable delivery — this is not a distributed pub/sub system with many subscribers, it's a 1:1 hub↔body link.** Building offset-tracked, bounded-window replay (the only version of "durable" seen anywhere in this research that isn't a full message broker) is a real subsystem for what is, at Holler's stated scale (one hub, one bound client, a handful of named sessions), a rare-edge-case race — a turn happening to complete in the exact window the socket is down. Over-engineering this is the wrong call for this project's scale.

Concretely: on reconnect, the client should re-advertise (fresh `presence`/`hello`) its current session list and **busy state**, not a queue of missed frames. If a turn finished while disconnected, the session's `busy: false` (protocol v1 §7, `status` document) is simply true on the next status check — meta-O (or the hub UI) sees "not busy anymore" and can `query`/re-`say` for the result, exactly as it would if it had been watching live and the reply had streamed by while nobody was looking. This mirrors mosh's philosophy directly (§3.7): **sync current state, don't replay history.**

This is the memo's one clear recommendation with reasoning attached; it is *not* asserted as an industry-mandated answer (no prior art in this survey does exactly Holler's shape), but it is the conservative, low-complexity choice consistent with every general-purpose realtime system surveyed that isn't itself a durable broker, and with ADR-0005's own axiom that session state — not transport state — is the thing that's supposed to survive.

A cheap enhancement that stops short of full durability, worth flagging as an option rather than baking in: the **client** (not the server) could hold the single most recent completed-but-undelivered reply per session in memory and flush it first on reconnect (bounded to "the last reply," not a queue) — cheap because the client already has the ACP session and its result in hand, no new storage subsystem required. Whether that's worth the small amount of extra client-side state versus pure ask-again is a genuine judgment call for the team (§5 below flags it as such).

## 5. Recommendation set

For each, a concrete number/policy, what it's grounded in, and whether it's an industry-standard-ish default or a Holler-specific judgment call.

**(a) Heartbeat interval — recommend ~15s.**
Grounded in the observed 3–30s range across Phoenix (30s), Buzz (30s ping), mosh (≤3s, but mosh is a keystroke-latency-sensitive interactive protocol, not comparable in cadence needs), and the websocket.org 30–45s / 75%-of-proxy-timeout rule. Holler defaults to loopback (no intervening proxy) and is mostly a local/LAN/tunnel tool, so the proxy-timeout constraint that drives other systems toward 30–45s doesn't bind as hard — but faster status feedback ("reconnecting…" in `holler status`) is a real UX want for a human watching a hub. **15s is a judgment call**, splitting the difference between Phoenix/Buzz's 30s convention and a snappier local-tool feel; nothing in the research mandates this exact number.

**(b) Missed-heartbeats-before-dead — recommend 3.**
This is the one number that's close to an industry constant: SSH's `ClientAliveCountMax`/`ServerAliveCountMax` default to 3, Buzz's own `SLOW_CLIENT_GRACE_LIMIT` is 3, and Buzz's ping/pong pattern is "3 missed pongs → disconnect." **Recommend adopting 3** as the default absent a reason otherwise — at a 15s heartbeat this means ~45s to declare a socket dead, in the same order of magnitude as Buzz's ~90s (30s × 3).

**(c) Reconnect backoff — recommend Full Jitter, base 500ms, cap 30s, uncapped attempt count.**
Full Jitter is the AWS-blog-proven best of the three published formulas (§3.2) — recommend it over the naive exponential-only or Equal Jitter alternatives on that evidence alone. `base=500ms` sits between Socket.IO's 1000ms and SignalR's 0ms-first-attempt; `cap=30s` matches SignalR's terminal step and is far below gRPC's 2-hour server keepalive ceiling — reasonable for a tool where "give up trying to come home" is not a design goal. **Recommend not capping the number of attempts** (matching Socket.IO's `Infinity` default) — the whole point of ADR-0005 is that the underlying agent session is durable and worth reconnecting to indefinitely; a client that stops retrying after N attempts contradicts that axiom. The exact base/cap numbers are a **judgment call**; the choice of Full-Jitter-with-uncapped-retries is grounded in cited evidence and in ADR-0005's own stated intent.

**(d) Resume with same session names, or re-advertise — recommend always re-advertise a fresh `presence`/`hello` on every (re)connect.**
The credential (`token_id`/`client_id`) is what persists across reconnects (ADR-0004, issue #24) — that's identity, already decided. But the **session list and busy state** should never be assumed carried over from before the drop: send a complete `hello`/`presence` frame fresh on every connection, every time. This is directly grounded in §3.9's "ask again, don't assume implicit continuity" pattern (none of Phoenix/Socket.IO/SignalR resume exact prior subscription state without an explicit, opt-in mechanism) and sidesteps any question of whether the server's roster row for this client survived the gap or already TTL'd out — the client's fresh advertisement is authoritative either way. This is a fairly clear industry-consistent recommendation, not a coin-flip judgment call.

**(e) In-flight reply completing mid-disconnect — recommend ask-again (§4), with client-side single-reply buffering flagged as an optional enhancement, not a requirement.**
See §4 for full reasoning. This is presented as the memo's clearest recommendation given Holler's stated scale, but the choice between bare ask-again and the cheap client-side single-reply buffer is a genuine **judgment call for the team** — it trades a small amount of client memory/complexity for not making a human re-`say` to see a reply that already finished.

**(f) Roster tri-state — recommend three states: `connected` / `reconnecting` (heartbeat missed, within TTL, backoff in progress) / gone (TTL expired, dropped from roster).**
This directly answers the brief's item (e) about representing "disconnected but maybe coming back" vs. "gone," and is consistent with ADR-0006's "bounded wrong dot, never an indefinite one." **No prior-art tool in this survey ships exactly this three-state shape** for a roster (Herdr doesn't have this problem yet in its shipped 1:1 model; Buzz just drops to Redis TTL expiry with no visible middle state cited in its docs) — this is a **Holler-specific design proposal**, not an industry-standard answer, though it's a natural synthesis of the heartbeat-TTL pattern (§3.3, §3.8) applied to a roster UI/CLI surface. Recommend the TTL for the `reconnecting → gone` transition be meaningfully longer than the heartbeat-dead threshold from (b) — e.g. on the order of a few backoff cycles' worth of time (a minute or few), so a client riding out a short network blip doesn't get evicted from the roster mid-backoff. The exact TTL number is left to issue #32, where server-side tuning is explicitly scoped to land.
